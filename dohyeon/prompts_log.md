# Keepy — AI 활용 기록 (prompts_log.md)

본 문서는 Keepy 개발 과정에서 AI 도구를 활용한 주요 사례와 제안에 대한 채택·수정 판단을 정리한 것이다. 프롬프트는 핵심 내용을 중심으로 요약하였으며, 개발 과정에서의 설계 결정과 문제 해결을 중심으로 기록하였다.

---

# MP1 — 목록 · 추가 · 완료

## 1. Flutter 프로젝트 아키텍처 설계

- **작성자:** 도현
- **프롬프트(요약):** "Flutter와 Firebase를 사용하는 4인 팀 프로젝트를 개발하려고 한다. 기능별 병렬 개발이 가능하도록 화면, 상태 관리, 데이터 접근 계층의 역할을 구분하고, 향후 Firebase 동기화와 OCR 기능을 확장할 수 있는 아키텍처와 폴더 구조를 설계해 줘."
- **AI 응답:** UI·상태 관리·데이터 접근 계층을 분리하고, Riverpod을 통한 상태 관리와 Repository 패턴을 활용하는 구조를 제안하였다. 또한 기능별 디렉터리와 공통 모듈을 구분하여 기능 확장 시 기존 코드의 변경을 최소화하도록 안내하였다.
- **판단:** **채택.** MP1부터 MP4까지 기능이 단계적으로 확장되는 프로젝트이므로 유지보수와 확장성을 고려한 구조가 필요하다고 판단하였다. 이를 바탕으로 `app`, `core`, `features` 구조와 Riverpod, go_router, Repository 패턴을 적용하였다.

# MP2 — 로컬 저장 및 CRUD 확장

## 1. 기존 Flutter 프로젝트 구조 분석

- **프롬프트:** "기존에 작성한 Keepy Flutter 프로젝트의 소스 코드를 분석해 줘. `TaskRepository`, `InMemoryTaskRepository`, `FirestoreTaskRepository`의 역할과 데이터 흐름을 확인하고, MP1 요구사항 중 이미 구현된 기능과 보완이 필요한 부분을 구분해 줘. 특히 앱 시작, 화면 이동, 상태 갱신이 어떻게 연결되는지 살펴보고 MP2 개발에 필요한 수정 파일을 파악해 줘."
- **AI 활용:** 기존 프로젝트의 클래스 구조와 Repository 패턴을 분석하고, MP1 기능 충족 여부 및 MP2 확장에 필요한 작업을 검토하도록 요청함.
- **판단 및 적용:** 기존 아키텍처를 전면 재작성하지 않고 재사용하는 방향을 선택함. 새로운 프로젝트를 생성하거나 불필요한 상태 관리 라이브러리를 도입하지 않고 기존 코드에서 필요한 부분만 확장하도록 개발 범위를 설정함.

## 2. 팀원 브랜치의 구현 방식 비교

- **프롬프트:** "GitHub에 있는 희일·현규·서윤 브랜치를 분석하고 MP1·MP2 구현 방식을 비교해 줘. 특히 태스크 데이터 관리, 로컬 저장, 상태 관리, 테스트 방식의 차이점을 살펴봐 줘. README에 작성된 내용만으로 구현 상태를 판단하지 말고 실제 소스 코드도 확인해 줘. 다른 팀원의 프로젝트를 그대로 복제하려는 것이 아니라 내 프로젝트에 참고할 만한 구현 방식을 찾는 것이 목적이야."
- **AI 활용:** 세 팀원의 프로젝트 구조와 구현 방식을 비교하도록 요청함. 특히 서윤 브랜치의 저장 요청 순서 관리와 데이터 복구 처리, 현규 브랜치의 로컬 우선 저장 및 동기화 구조 등을 주요 검토 대상으로 지정함.
- **판단 및 적용:** 다른 팀원의 완성된 코드를 병합하는 대신 기존 개인 프로젝트를 유지하는 방향을 선택함. 팀원의 구현 방식은 필요한 부분만 참고하고, 실제 동작이 검증되지 않은 기능은 문서상 구현 여부와 구분하도록 함.

## 3. Repository 아키텍처 및 로컬 저장 방식 검토

- **프롬프트:** "기존 `TaskRepository` 인터페이스를 유지하면서 로컬 영구 저장 기능을 확장하는 구조가 적합한지 검토해 줘. 현재 `Task` 모델과 Repository 구현체를 분석하고, `shared_preferences`를 사용하는 방식과 SQLite 등의 대안을 비교해 줘. 향후 MP3에서 Firestore 동기화를 추가할 예정이므로 기존 데이터 관리 구조와의 호환성도 고려해 줘."
- **AI 활용:** 로컬 저장 기술의 선택 기준과 기존 Repository 패턴을 활용하는 설계 방향을 검토하도록 요청함. 데이터 모델의 JSON 직렬화, 저장소 구현체 분리, 향후 Firestore 연동 가능성 등을 검토 대상으로 포함함.
- **판단 및 적용:** 현재 프로젝트의 규모와 데이터 구조를 고려해 `shared_preferences`를 우선 사용하는 방향으로 결정함. 기존 Repository 인터페이스와 Firestore 관련 코드를 유지하고 MP2에서는 로컬 저장 기능의 완성도를 우선하도록 함.

## 4. Flutter 실행 및 데이터 영속성 검증

- **프롬프트:** "MP2 개발 결과를 실제 Flutter 앱에서 검증해 줘. `flutter analyze`, `flutter test`, `flutter run -d chrome`을 활용하고, 태스크 추가·수정·삭제·완료 상태 변경과 필터 전환이 정상적으로 작동하는지 확인해 줘. 특히 앱을 종료하고 다시 실행했을 때 데이터가 유지되는지 검증하고, 테스트를 실행하지 못했다면 성공했다고 기록하지 말아 줘."
- **AI 활용 및 검증:** 정적 분석, 자동 테스트, 실제 앱 실행을 구분하여 검증하도록 요청함. 앱 재실행 후 데이터 복원과 삭제·수정 상태 유지 여부를 주요 테스트 조건으로 설정함.
- **판단 및 적용:** Chrome에서 Flutter 앱을 실행하고 새로고침 및 재실행 후에도 로컬 데이터가 유지되는 것을 직접 확인함. 웹 실행 포트가 변경되면 기존 데이터가 보이지 않을 수 있어 동일한 포트에서 재검증함. 자동 테스트 결과는 별도로 확인되지 않아 통과 여부를 기재하지 않음.

# MP3 — Firebase 동기화 및 멀티플랫폼 확장

## 1. 기존 Firebase 코드 분석 및 재사용 검토

- **프롬프트:** "기존 Keepy 프로젝트의 Firebase 관련 코드를 먼저 분석해 줘. `main.dart`의 Firebase 초기화 및 익명 로그인 방식, `FirestoreTaskRepository`의 구현 범위, Riverpod Provider와 데이터 저장소의 연결 구조를 확인해 줘. 특히 기존 MP2의 로컬 저장소와 Firestore 저장소가 어떻게 구분되어 있는지, 실시간 동기화와 오프라인 처리가 어디까지 구현되어 있는지 파악해 줘."
- **AI 활용:** 기존 Firebase 연동 코드와 데이터 흐름을 분석하고, 이미 구현된 기능과 추가 작업이 필요한 부분을 구분하도록 요청함.
- **판단 및 적용:** 기존 프로젝트에서 Firebase 초기화와 익명 로그인이 동작하는 것을 확인한 상태였으므로, 새로운 구조를 처음부터 작성하지 않고 기존 코드를 재사용하는 방향으로 결정함. 기존 MP2 기능과 Riverpod 구조를 유지하고 필요한 부분만 수정하도록 지시함.

## 2. Android 및 iOS 플랫폼 지원 추가

- **프롬프트:** "현재 Web 전용으로 구성된 Flutter 프로젝트에 Android와 iOS 플랫폼 지원을 추가해 줘. 기존 코드를 유지하면서 `flutter create --platforms=android,ios .` 명령어를 활용할 수 있는지 확인하고, 생성되는 플랫폼 설정이 기존 파일에 영향을 주지 않는지 검토해 줘. `flutter doctor -v`로 개발 환경을 점검하고 Android SDK, 패키지 호환성, Application ID와 Bundle ID도 확인해 줘."
- **AI 활용:** 기존 프로젝트에 모바일 플랫폼을 추가하는 방법과 플랫폼별 빌드 설정을 검토하도록 요청함. 특히 Windows 환경에서 iOS 빌드 및 실행을 검증할 수 없는 제약도 고려하도록 함.
- **판단 및 적용:** 별도의 모바일 앱을 새로 만드는 대신 Web·Android·iOS가 하나의 Flutter 코드베이스를 공유하도록 개발 방향을 설정함. 기존 Flutter SDK 버전과 Web 프로젝트를 보존하고, 실제 실행하지 못한 플랫폼은 검증 완료로 기록하지 않도록 지시함.

## 3. Firebase 멀티플랫폼 초기화 및 환경 설정 검토

- **프롬프트:** "기존 Firebase 프로젝트 `keepy-mp3`를 유지하면서 Android와 iOS에서도 Firebase를 사용할 수 있도록 설정 구조를 검토해 줘. 현재 Web용으로 생성된 `firebase_options.dart`와 `USE_FIREBASE` 환경 변수 기반 초기화 방식이 어떻게 연결되어 있는지 분석하고, 플랫폼별 설정이 중복되거나 충돌하지 않도록 정리해 줘. Firebase 설정값 중 공개 가능한 정보와 비밀정보도 구분하고, `.env.example` 및 `--dart-define` 활용 방식도 확인해 줘."
- **AI 활용:** FlutterFire 설정 파일과 기존 Firebase 초기화 방식의 관계, 플랫폼별 설정 방법, 환경 변수 및 제출용 설정 파일 관리 방식을 검토하도록 요청함.
- **판단 및 적용:** 기존 Firebase 프로젝트를 그대로 사용하고 플랫폼별 설정만 확장하는 방향을 선택함. 원격 Firebase 설정을 변경하거나 새로운 앱을 등록하는 작업은 사용자 승인 후 진행하도록 제한하고, 설정 파일을 제외하더라도 실행 환경을 재구성할 수 있도록 요구함.

## 4. 오프라인 캐시 및 동기화 충돌 정책 검토

- **프롬프트:** "Firestore의 오프라인 캐시와 기존 MP2 로컬 저장 기능이 함께 사용될 때 문제가 발생할 수 있는지 검토해 줘. Web과 Android/iOS에서 오프라인 데이터가 유지되는 방식의 차이를 확인하고, 중복 저장이나 동기화 충돌을 방지할 방법을 분석해 줘. 여러 기기에서 동일한 태스크를 수정하는 경우에는 LWW(Last Write Wins) 같은 단순한 충돌 해결 정책을 우선 검토하되, 오프라인 수정 순서나 삭제한 태스크가 다시 나타나는 문제도 고려해 줘."
- **AI 활용:** Firestore SDK의 오프라인 캐시와 보류 중인 쓰기 동기화 기능을 검토하도록 요청하고, 기존 로컬 저장소와의 관계 및 데이터 충돌 가능성을 분석 대상으로 지정함.
- **판단 및 적용:** 별도의 복잡한 동기화 시스템을 처음부터 구현하기보다 Firestore SDK가 제공하는 기능을 우선 활용하도록 설계 방향을 설정함. 충돌 해결 정책은 단순성과 일관성을 기준으로 검토하되, 실제 코드의 동작과 문서에 기록한 정책이 일치하도록 요구함.

## 5. 멀티 디바이스 동기화 및 플랫폼별 검증

- **프롬프트:** "MP3 기능이 정상적으로 동작하는지 실제 실행 환경에서 검증해 줘. 동일 계정으로 로그인한 브라우저 A와 B 사이에서 태스크 추가·수정 결과가 반영되는지 확인하고, 인터넷 연결을 끊은 상태에서 작성한 태스크가 온라인 복귀 후 Firestore에 저장되는지도 테스트해 줘. 기존 MP2 기능에 문제가 없는지 확인하고 `flutter analyze`, `flutter test`, `flutter build web`, `flutter build apk`를 실행해 줘. 실행하지 못한 테스트는 성공으로 기록하지 말고 이유를 구분해 줘."
- **AI 활용:** 계정별 데이터 분리, 여러 기기 간 동기화, 오프라인 복구, 기존 기능 유지 여부를 확인하기 위한 테스트 시나리오를 제시함. 플랫폼별 빌드 및 정적 분석도 검증 항목에 포함함.
- **판단 및 적용:** 단순히 코드가 작성되었다는 사실만으로 MP3가 완성되었다고 판단하지 않고, 실제 데이터 동기화와 오프라인 복구 여부를 확인하도록 검증 기준을 설정함. Windows에서 수행하기 어려운 iOS 실행 테스트는 별도로 구분하도록 했으며, 구체적인 테스트 통과 결과는 확인된 실행 내역이 없어 기재하지 않음.
