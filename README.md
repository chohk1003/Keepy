# Keepy (키피) — 여러 기기에서 같은 목록을 보는 할 일 앱

> 주제 #2109 할 일 앱 – BaaS, AI 활용 · **미니프로젝트 3단계: 백엔드 서비스로 동기화하기**
> (1단계 '화면 만들기', 2단계 '저장되는 앱' 결과물 위에 이어서 작업 · 앱 버전 0.6.0)

Keepy 는 Flutter 로 만든 할 일 앱입니다. 1·2단계에서 기기 안에 저장하던 할 일을 **Supabase 서버로 올려**,

**인터넷이 돌아오면 자동으로 서버에 반영**합니다.

## 1. 실행 절차

**필요한 것:** Flutter stable 3.47.9 (팀 공통) · Chrome · Supabase 무료 계정. 자세한 순서는 [실행 매뉴얼](docs/MP3_실행_매뉴얼.md).

```powershell
cd C:\Keepy1\app

# 1) 처음 한 번: 플랫폼 폴더 생성 + 패키지 설치 (android/ios/web, 인터넷 권한 포함)
powershell -ExecutionPolicy Bypass -File tool\setup_platforms.ps1

# 2) 설정 키: 예시를 복사해 .env 를 만들고 Supabase 주소·공개 키를 채운다 (5절)
Copy-Item .env.example .env
notepad .env

# 3) 검사
flutter analyze
flutter test

# 4) 실행 — 반드시 --dart-define-from-file=.env 를 붙인다 (안 붙이면 동기화 꺼짐 = 2단계와 같음)
flutter run -d chrome --dart-define-from-file=.env

# 두 기기 확인: 웹 서버로 띄우고 서로 다른 브라우저 두 개(예: Chrome·Edge)로 같은 주소를 연다
flutter run -d web-server --web-port 8080 --dart-define-from-file=.env
```

앱에서: **설정 > 계정**(또는 메인 오른쪽 위 ☁ 아이콘) → 회원가입/로그인 → 다른 기기에서 같은 계정으로 로그인.

## 2. 선택한 BaaS 와 이유 — Supabase

| 기준 | **Supabase** (선택) | Firebase (Cloud Firestore) |
|---|---|---|
| 데이터 모델 | PostgreSQL 표 + SQL · 서버 트리거 | 문서(JSON) 컬렉션 |
| 충돌 규칙을 서버에서 강제 | **트리거 한 개로 '더 오래된 쓰기 무시'** 를 DB 가 보장 | 보안 규칙·트랜잭션으로 직접 구성 |
| 사용자별 데이터 분리 | 행 단위 보안(RLS) 정책 3줄 | 보안 규칙 작성 |
| Flutter 연결 | REST 라 `http` 패키지 하나로 충분 (플랫폼 설정 없음) | `flutterfire configure`, `google-services.json`·`GoogleService-Info.plist`, 플랫폼별 설정 |
| 웹(Chrome) 실행 | 그대로 됨 | 웹 앱 등록·설정 추가 |
| 무료 요금제 | DB 500MB, 월 활성 사용자 5만 | 일일 읽기/쓰기 횟수 제한 |
| 콘솔에서 확인 | Table Editor 에서 표로 바로 확인 (제출 스크린샷) | Firestore 콘솔 |

**선택 이유**
1. **충돌 처리를 서버가 보장한다** — `updated_at` 이 더 오래된 쓰기를 무시하는 트리거(`app/supabase/schema.sql`)로,
   오프라인이던 기기가 늦게 올려도 최신 내용을 덮지 못한다. 앱 버그가 있어도 서버 규칙은 지켜진다.
2. **기존 앱과 충돌이 없다** — 공식 SDK 대신 REST 를 직접 불러 `http` 패키지 하나만 더했다. 1·2단계의 OCR(ML Kit)·
   이미지 패키지, 안드로이드·iOS·웹 설정을 건드리지 않아 빌드가 깨질 여지가 가장 적다.
3. **웹까지 같은 코드** — 팀원 모두 `flutter run -d chrome` 으로 확인해 왔고, 두 브라우저로 '두 기기' 를 바로 재현할 수 있다.
4. **SQL 한 파일로 재현** — 팀원 누구나 SQL Editor 에 붙여 넣으면 같은 백엔드가 만들어진다(여러 번 실행해도 안전).

## 3. 동기화 구조

```
 기기 A                                    Supabase                                   기기 B
┌──────────────┐  ① 변경 감지           ┌─────────────────────────┐           ┌──────────────┐
│ TaskStore    │──► 동기화 장부(대기열)  │ Auth (이메일·비밀번호)    │           │ TaskStore    │
│ (2단계 그대로)│    기기에 저장          │ keepy_tasks             │           │              │
│              │  ② 당겨오기 ◄──────────│  user_id·id·data(JSON)  │──────────►│ ② 당겨오기    │
│              │  ③ 올리기   ──────────►│  deleted·updated_at     │◄──────────│ ③ 올리기      │
└──────────────┘                         │  synced_at  + RLS + 트리거│           └──────────────┘
                                         └─────────────────────────┘
```

| 단계 | 하는 일 | 코드 |
|---|---|---|
| ① 변경 감지 | 할 일이 바뀔 때마다 할 일별 JSON 을 장부와 비교 → 새로 생김·바뀜·사라짐(삭제)을 '올릴 변경' 으로 표시. 장부는 기기에 저장(앱을 꺼도 대기열 유지) | `state/sync_controller.dart` `_markLocalChanges` |
| ② 당겨오기 | 서버에서 **마지막으로 받은 뒤 새로 들어온 줄만**(`synced_at` 기준) 받아 반영 | `_pull`, `_applyRemoteRows` |
| ③ 올리기 | 대기열을 한 번에 올리고 성공한 것만 대기열에서 뺌 | `_push` |
| 언제 | 앱 시작, 앱이 다시 앞으로 올 때, 할 일을 바꾼 1.2초 뒤, 20초마다, '지금 동기화' 버튼. 오프라인이면 10초마다 재시도 | `syncNow`, `_schedule` |

## 4. 동기화 충돌 처리 방침

| 상황 | 처리 | 이유 |
|---|---|---|
| **두 기기에서 같은 할 일을 고침** | 할 일 단위 **마지막 수정 우선(Last-Write-Wins)**. 각 변경에 기기 시각(`updated_at`, 밀리초)을 붙이고 **큰 쪽이 이긴다**. 앱(받을 때)과 서버(트리거, 쓸 때) 양쪽에서 같은 규칙 적용 | 할 일은 제목·완료·기한이 짧은 항목이라 필드별 병합보다 단순하고 예측 가능 |
| 먼저 고친 기기가 **나중에** 올림 (오프라인이었음) | 서버 트리거가 더 오래된 쓰기를 **무시** → 다음 동기화 때 최신 내용을 받아 맞춰짐 | 늦게 온 옛 내용이 최신을 덮지 않음 |
| **삭제** | 줄을 지우지 않고 **삭제 표시(`deleted = true`)** 를 올림 → 다른 기기에서도 지워짐. 서버의 실제 DELETE 는 권한으로 막음 | 지운 사실이 전해져야 다른 기기에서 다시 살아나지 않음 |
| 한 기기는 지우고, 다른 기기는 **더 나중에** 고침 | 나중에 고친 쪽이 이겨 **되살아남** (같은 LWW 규칙) | 사용자의 마지막 의도를 따름 |
| **오프라인에서 작성·수정·삭제** | 기기 장부(대기열)에 쌓아 두고, 연결되면 **자동으로 올림**. 앱을 꺼도 대기열 유지. 화면에 '오프라인 · 올릴 변경 N개' 표시 | 통과 기준 2 |
| 올리는 **도중** 또 고침 | 올린 시점의 버전과 같을 때만 대기열에서 뺌 → 새 변경은 다음에 다시 올라감 | 변경 유실 방지 |
| **로그인할 때 이 기기에 할 일이 있었음** | 계정에 **합침**. 이때 기준 시각은 '지금' 이 아니라 **할 일의 마지막 수정 시각** | 오래 안 쓴 기기가 로그인하면서 최신 내용을 덮지 않게 |
| 받은 변경 | 서버에서 온 변경은 대기열에 넣지 않음 | 같은 내용이 기기↔서버를 계속 오가지 않게 |

**한계와 대응:** 기기 시계가 크게 틀리면 LWW 판정이 어긋날 수 있다(같은 할 일을 몇 초 안에 두 기기에서 고칠 때만 문제).
같은 할 일의 기록 시각은 항상 앞으로만 가게 했고(`_stamp`), 할 일 단위라 다른 할 일에는 영향이 없다.
실시간 반영(Realtime 구독)은 넣지 않았다 — 통과 기준이 '새로고침 후 표시' 이고, 20초 주기·앱 복귀·'지금 동기화' 로 충분하다.

## 5. 백엔드 설정 절차 (Supabase)

1. https://supabase.com 가입 → **New project** (Region: Northeast Asia (Seoul) 권장, DB 비밀번호는 따로 보관).
2. 왼쪽 **SQL Editor → New query** → [`app/supabase/schema.sql`](app/supabase/schema.sql) 전체를 붙여 넣고 **Run**.
   테이블 `keepy_tasks`, 행 단위 보안(RLS) 정책 3개, 마지막 수정 우선 트리거가 만들어진다.
3. **Authentication → Sign In / Providers → Email**: Email 사용 켜짐 확인. 과제 시연용으로는 **Confirm email 끄기**
   (켜 두면 가입 후 메일의 확인 링크를 눌러야 로그인 가능).
4. **Project Settings → API Keys**(또는 Data API)에서 **Project URL** 과 **Publishable key**(`sb_publishable_…`)
   — 또는 Legacy 탭의 `anon` `public` 키 — 를 복사.
5. `app/.env` 에 붙여 넣기 (6절). Secret key·`service_role` 키는 절대 쓰지 않는다.

## 6. 설정 키 관리 (하드코딩 금지)

| 파일 | 내용 | Git |
|---|---|---|
| `app/.env.example` | 필요한 키 이름만 (`SUPABASE_URL=`, `SUPABASE_ANON_KEY=`) + 설명 | **제출** |
| `app/.env` | 실제 값 | `.gitignore` 로 **제외** (최상위·app 둘 다) |

- 앱은 값을 코드에 적지 않고 실행할 때 `--dart-define-from-file=.env` 로 받는다 → `String.fromEnvironment` (`app/lib/core/env.dart`).
- 값이 없으면 앱은 오류 없이 **동기화가 꺼진 채** 실행되고, 설정 > 계정에서 켜는 방법을 안내한다.
- 확인: `git status` 에 `.env` 가 보이지 않아야 하고, 저장소에서 `supabase.co`·`sb_publishable_`·`eyJ` 를 검색해 나오지 않아야 한다.

## 7. 구현 기능

### 3단계 (MP3) — 서버 동기화
| 기능 | 설명 |
|---|---|
| **회원가입·로그인·로그아웃** | 설정 > 계정 시트. 이메일·비밀번호(6자 이상), 한국어 오류 안내, 로그인 상태는 기기에 저장(다시 켜도 유지), 토큰 만료 전 자동 갱신 |
| **서버 저장·조회** | Supabase `keepy_tasks` 표에 할 일 저장, 새로 들어온 줄만 받아 반영 |
| **두 기기 동기화** | 같은 계정 기기끼리 추가·수정·완료·삭제·순서·태그가 모두 맞춰짐 |
| **오프라인 → 온라인** | 대기열(기기 저장) → 연결되면 자동 반영, 오프라인이면 10초마다 재시도 |
| **상태 표시** | 메인 오른쪽 위 ☁ 배지(✓ 맞춰짐 / ↻ 동기화 중 / ↑N 올릴 변경 / 오프라인 / 오류), 계정 시트에 마지막 동기화·올릴 변경 수·지금 동기화 |
| **충돌 처리** | 4절 (마지막 수정 우선 + 삭제 표시 + 서버 트리거) |
| **키 분리** | 6절 |

## 10. (2단계) 저장 방식 — 대안 비교와 선택 이유

| 방식 | 장점 | 단점 | Keepy 에 맞나 |
|---|---|---|---|
| **shared_preferences** (선택) | 설정 거의 없이 바로 사용, Android·iOS·**웹**·데스크톱 모두 지원, 코드 생성 불필요 | 키-값 저장이라 검색·정렬 쿼리 없음, 저장할 때마다 목록 전체를 다시 씀, 대용량 부적합 | ◎ 데이터가 작고 구조가 단순 |
| sqflite (SQLite) | 표·인덱스·SQL 쿼리, 대용량·부분 수정에 강함 | 웹 기본 미지원, 테이블 설계·SQL·마이그레이션 코드 필요 | △ 지금 규모엔 과함 |
| Hive / Isar | 빠름, 객체 단위 저장 | 어댑터·코드 생성 필요, 유지보수 상태 확인 필요 | △ |
| drift | 쿼리 타입 검사, 반응형 스트림 | 코드 생성·학습 비용 | ✕ |
| JSON 파일 | 형식 자유 | 파일 입출력·깨짐 처리 직접 구현, 웹 미지원 | △ |

선택 이유: 데이터가 작고 단순(할 일 1개 ≈ 200바이트) · 모든 실행 환경에서 같은 코드 · 설정·코드 생성 없음 ·
화면은 `TaskRepository` 인터페이스만 쓰므로 바꾸기 쉬움. 3단계에서도 **기기 저장은 그대로 두고** 그 위에 동기화를 얹었다
(오프라인에서 완전히 동작하는 이유). 저장 키: `keepy.tasks.v1`(할 일), `keepy.settings.v1`(설정),
`keepy.sync.ledger.v1`(동기화 장부·대기열, 3단계), `keepy.sync.session.v1`(로그인 상태, 3단계).
